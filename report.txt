Abstract
Career development today is fragmented across disconnected platforms: job seekers search vacancies on multiple boards, guess at the skills a role requires, hunt for learning resources of uncertain quality, rewrite resumes by hand, and rehearse interviews inadequately or not at all. PathCompanion AI addresses this fragmentation with a single full-stack web application in which six cooperating AI agents — Job Scout, Skill Gap Analyzer, Learning Resource Finder, Resume Architect, Mock Interview with Panic Control, and Career Path Planner — share a common memory and react to one another through an event bus, while remaining fully usable as standalone modules.
The system adopts a hybrid intelligence design. Two custom machine-learning models were trained specifically for this project: (1) a resume-category classifier, a fine-tuned DistilBERT trained on the Kaggle Resume Dataset (2,484 resumes, 24 occupational categories), achieving 82.3% test accuracy and 0.751 macro-F1 against a TF-IDF + Logistic Regression baseline of 65.5% and 0.596; and (2) a multi-label skill-extraction model trained over a 25-skill vocabulary using LLM-assisted weak labelling of ~11,800 public job postings. These trained models handle the core structured-analysis tasks, while free-tier large language models (Google Gemini Flash, Groq Llama 3.3 70B, Groq Whisper) handle open-ended generation, conversation, and speech.
The application is implemented with React 18 (Vite) on the frontend, FastAPI (Python 3.11) on the backend, and Supabase (PostgreSQL with pgvector) as the data tier, using 13 relational tables protected by row-level security and HNSW vector indexes for semantic job matching. This report presents the complete engineering lifecycle — planning, requirement gathering and analysis, system design, implementation, and testing and validation — together with a quantitative evaluation of the trained models and an honest discussion of limitations and future work.

1.0 Introduction
1.1 Background Studies
The global employment landscape is undergoing structural transformation. Rapid technological change has shortened the shelf life of professional skills, while job vacancies are scattered across dozens of platforms (LinkedIn, Indeed, Glassdoor, specialised remote-work boards) and learning resources across an equally bewildering range of providers. The result is a persistent talent gap: employers struggle to find suitably skilled candidates, while capable individuals cannot easily identify which skills they lack, where to learn them, or how to present themselves convincingly. Graduates and career-changers — particularly in developing economies such as Sri Lanka — rarely have access to affordable career coaching.
The recent maturation of large language models (LLMs) and agentic orchestration frameworks makes conversational and generative career support feasible at near-zero cost through generous free tiers (Google Gemini, Groq). However, relying solely on third-party LLMs is neither robust nor academically sufficient. PathCompanion AI therefore adopts a hybrid intelligence design in which two custom-trained machine-learning models handle the well-defined classification and extraction tasks at the system's core, while LLMs handle open-ended generation and conversation. This reduces external dependency, improves reproducibility, and demonstrates an end-to-end machine-learning engineering workflow alongside full-stack software engineering.
1.2 Problem Statement
Career development today is fragmented across disconnected tools. A typical job seeker must search multiple job boards manually, guess which skills a posting truly requires, search separately for courses of uncertain quality, rewrite their resume by hand for every application, practise interviews with friends or not at all, and track professional growth in their head. No mainstream tool connects these steps, so insight generated in one stage is never propagated to the others.
Six key issues define the problem space:
Job discovery is inefficient — relevant openings are buried across many platforms, and keyword search fails to capture semantic matches (a 'Frontend Engineer' vacancy will not surface for a 'React developer' profile).
Skill gaps are invisible — candidates receive no structured feedback on which specific skills separate them from a target role, or how important each missing skill is.
Learning is unguided — free, high-quality resources exist (freeCodeCamp, MDN, official documentation) but sequencing them into a coherent study path requires expertise the learner does not yet have.
Resumes are generic — applicant-tracking systems (ATS) reward keyword alignment with each specific job description, yet applicants send one resume everywhere.
Interview anxiety is unaddressed — candidates have no safe, realistic environment to rehearse spoken interviews; existing mock-interview tools are text-only, scripted, and disconnected from the actual job.
Career progression is opaque — professionals do not know which role follows their current one, which skills it demands, or how long the transition should take.
1.3 Objective
The main objective is to design, implement, and evaluate a full-stack, multi-agent AI web application that provides end-to-end career support through six cooperating agents sharing a common memory, with two custom-trained machine-learning models at the core of its resume and skill-gap intelligence, operable both as interconnected workflows and as standalone modules.
The specific, measurable sub-objectives were:
Design a normalised PostgreSQL (Supabase) schema with pgvector embeddings serving as shared memory for all agents, with row-level security per user.
Train and evaluate a resume-category classification model on the Kaggle Resume Dataset (2,484 labelled resumes, 24 categories), benchmarked against a TF-IDF baseline.
Train and evaluate a multi-label skill-extraction model over a curated skill vocabulary using LLM-assisted weak labelling of public job-description text.
Implement automated job aggregation from free public job APIs with hybrid semantic + skill-overlap matching.
Implement skill-gap analysis, ordered learning plans, ATS-optimised resume generation, a voice-based mock-interview agent with panic control, and long-term career-path planning.
Demonstrate the interconnected cascade: marking a skill as learned automatically refreshes gap analyses and flags affected resume drafts within 30 seconds without blocking the UI.
Operate the entire system within the free-tier limits of all external services.
1.4 Solutions
The proposed solution is a web application composed of a React (Vite) frontend, a FastAPI (Python) backend, and a Supabase (PostgreSQL + pgvector) database, whose intelligence layer is deliberately hybrid. Each of the six problems above is answered by a dedicated agent: the Job Scout aggregates vacancies from free public APIs and matches them semantically to the user's profile; the Skill Gap Analyzer uses the custom-trained skill-extraction model to partition skills into present and missing with importance ratings; the Learning Resource Finder converts each gap into an ordered study path of free resources with progress tracking; the Resume Architect uses the custom-trained resume classifier and generates ATS-optimised tailored resumes per job; the Mock Interview agent conducts realistic spoken interviews with adaptive questions, per-answer feedback and a panic-control feature; and the Career Path Planner maps the next role, its required skills, and a realistic timeline.
Crucially, the agents operate over shared memory and an event bus: when the user marks a skill as learned, the system automatically refreshes stale gap analyses and flags affected resume drafts — a cascade triggered by a single user action, while every module remains fully usable on its own. During development, a mock-exam module with e-mailed certificates was added beyond the original proposal scope.
2.0 Literature Review
2.1 Fragmentation of Career Tooling
Mainstream career tools each solve one slice of the problem. Job boards (LinkedIn, Indeed, Glassdoor, Remotive) index vacancies but provide limited skill-level feedback; resume builders (Zety, Novoresume) format documents but do not tailor content per job description; course platforms (Coursera, Udemy, freeCodeCamp) teach skills but are disconnected from the learner's actual gap; and mock-interview tools are predominantly text-based, scripted, and unaware of the specific job the candidate targets. No mainstream tool propagates insight generated in one stage (a newly learned skill) to the others (the resume, the job matches, the interview preparation). This integration gap is the central motivation for the present system.
2.2 Agentic AI Systems
The maturation of large language models and orchestration frameworks (LangGraph, LangChain) has made multi-agent architectures practical: specialised agents with distinct responsibilities coordinate through shared state rather than direct invocation (LangChain Inc., 2025). The design used here — agents that never call one another directly but write to shared memory and emit events — follows the event-driven pattern widely recommended for loosely coupled multi-agent systems, and preserves the ability to use every module standalone.
2.3 Text Classification and Transfer Learning
Transformer-based transfer learning is the established approach for text classification. DistilBERT (Sanh et al., 2019) retains roughly 97% of BERT's language-understanding capability with 40% fewer parameters and 60% faster inference, making it well suited to free-GPU training environments (Google Colab) and lightweight backend serving. Classical baselines — TF-IDF features with Logistic Regression or linear SVM — remain important reference points: comparing a fine-tuned transformer against such a baseline quantifies the benefit of contextual representations (Pedregosa et al., 2011).
2.4 Skill Extraction and Weak Supervision
Skill extraction from job postings is an active research area. Because manual span-level annotation is impractical at scale, weak supervision — programmatically or LLM-generated labels over large corpora, with a smaller manually verified gold set — is a well-established strategy (Zhang, Jensen and Plank, 2022). The ESCO taxonomy (European Commission) provides a standards-aligned label space of ~13,900 skills; restricting the label set to a curated high-frequency subset keeps multi-label classification tractable for an individual project while remaining interoperable.
2.5 Semantic Retrieval with Vector Databases
Dense embeddings enable semantic matching that keyword search cannot: a 'Frontend Engineer' vacancy can surface for a 'React developer' profile. pgvector adds vector similarity search to PostgreSQL, and HNSW indexes provide fast approximate nearest-neighbour retrieval, allowing job-to-profile matching within the same relational database that stores all other user data (Supabase, 2026). The hybrid scoring approach used here (embedding similarity plus explicit skill overlap) follows common practice in retrieval systems that combine dense and sparse signals.
2.6 Speech Interfaces for Interview Practice
Interview anxiety measurably degrades performance, and rehearsal in a realistic spoken setting reduces it. Modern speech pipelines make this feasible at zero cost: Whisper-class models provide accurate speech-to-text, neural TTS provides natural-sounding questions, and low-latency LLM inference (Groq) keeps the conversational loop under the ~2-second threshold at which spoken dialogue feels natural.

3.0.5 Life Cycle Model
The project followed an Agile (Scrum-based) life cycle with two-week sprints. Agile was selected over a plan-driven (waterfall) model for three reasons. First, the project combines two workstreams with inherent uncertainty — machine-learning model development (where achievable accuracy is unknown until experiments run) and multi-agent application development (where free-tier API behaviour emerges during integration) — and short iterations allow early course correction. Second, the module requires demonstrable progress at supervision meetings; each sprint concludes with a working increment. Third, requirements were maintained as a prioritised backlog with MoSCoW classification, allowing scope to flex (the mock-exam module was added; two agents were consciously deferred to future work) without endangering the core deliverables.
Each of the eight phases maps to one sprint of two weeks: sprint reviews assessed the increment against the measurable sub-objectives, and retrospectives fed process improvements into subsequent sprints. Version control used Git with feature branching; user stories followed the 'As a [role], I want [capability], so that [benefit]' format with acceptance criteria defined before implementation.

4.2 Requirement Gathering and Analysis
4.2.1 Requirement Gathering technique used for the project
Three complementary techniques were used. (1) A questionnaire distributed to final-year students, recent graduates, and early-career professionals to quantify the prevalence of the six problem areas and prioritise features. (2) Semi-structured interviews with a smaller set of job seekers to explore pain points in depth — particularly interview anxiety and resume tailoring behaviour. (3) Document and platform analysis of existing tools (job boards, resume builders, course platforms, mock-interview tools) to identify the integration gap that no mainstream tool covers. The combination provides quantitative breadth, qualitative depth, and competitive grounding.

5.0 System Design
5.1 Architecture Diagram
The architecture comprises three tiers plus a model-inference component (Figure 1). The presentation tier (React 18 + Vite) renders a dashboard, per-agent workspaces, and a persistent chat panel, communicating with the backend over REST (JSON) and Server-Sent Events for streamed responses, and directly with Supabase for authentication. The application tier (FastAPI) exposes versioned routers per agent and hosts the ML inference module that loads both trained models and serves them as internal prediction functions. The data tier (Supabase PostgreSQL with pgvector) holds thirteen relational tables plus the agent_events table that functions as the shared event bus. Agents never invoke one another directly; they write to shared memory and emit events, which both enables the interconnected cascade and preserves standalone operation of every module.
Figure 1: Three-tier system architecture with ML inference module and external services
5.2 ER Diagram
Figure 2 presents the entity-relationship model implemented in db/schema.sql: thirteen tables anchored on Supabase's auth.users. The design has three notable features. First, shared memory: the skills table is read and written by multiple agents (manual entry, resume parsing, learning completion), and its source column records provenance. Second, semantic columns: job_postings and resumes carry 768-dimension vector embeddings with HNSW indexes for cosine-similarity retrieval. Third, the event bus: agent_events records typed events (e.g., skill_learned) with a processed flag, decoupling event producers from consumers. All per-user tables enforce row-level security (auth.uid() = user_id); the job catalogue is a shared read-only resource written only by the backend service role. A database trigger auto-creates a profile row on user registration.

6.2 Design patterns
Layered architecture (router → service → data): routers handle HTTP concerns only; services encapsulate business logic; the data tier is accessed through the Supabase client. This separation keeps each layer independently testable.
Facade: GeminiService and GroqService wrap all LLM provider interaction behind small interfaces (generate_text, generate_json, chat, transcribe), so a provider change touches one class.
Singleton-style model loading: MLModelService loads both trained models once at startup and serves all predictions from memory, avoiding per-request deserialisation.
Event-driven observer (publish–subscribe): agents publish typed events to the agent_events table and consumers react asynchronously — the backbone of the interconnected cascade, chosen over direct calls to preserve standalone modules and idempotent re-processing.
Repository-style data access: services own all table access for their domain, keeping SQL/PostgREST calls out of routers.
6.3 Implementation of the program
6.3.1 Backend Structure
The backend follows the router–service separation designed in Section 5.3.2. Nine routers (jobs, skillgap, learning, resume, interview, career, exam, chat, assistant) validate requests with Pydantic models and delegate to services. Services encapsulate: job aggregation and upserting (jobs.py), hybrid matching with cosine similarity over pgvector embeddings (matching.py), embedding generation (embeddings.py), LLM access (gemini.py, groq_svc.py), interview question generation, coaching and feedback (interview.py), learning-plan and career-path generation (learning.py, career.py), certificate e-mail delivery (email_svc.py), and model inference (ml_models.py). Long-running operations return immediately and complete in the background, in line with NFR-03.
6.3.2 ML Model 1 — Resume Category Classifier
Dataset: the Kaggle Resume Dataset — 2,484 labelled resumes across 24 occupational categories (Information-Technology, Engineering, Finance, HR, Healthcare and others). Preprocessing: lowercasing; removal of URLs, e-mail addresses, punctuation and stop-words; label encoding; stratified 90/10 train/test split (2,235 / 249). Baseline: TF-IDF features with Logistic Regression. Transformer: DistilBERT (distilbert-base-uncased) fine-tuned for multi-class classification with a maximum sequence length of 256 tokens. Both models were trained in a version-controlled Colab notebook (ml/Model1_Resume_Classifier.ipynb); the baseline is serialised with joblib and served from backend/models/, and the fine-tuned weights are exported via save_pretrained for transformer serving.
6.3.3 ML Model 2 — Skill-Extraction Model
Label space: the 25 highest-frequency skills derived from ESCO-aligned skill mentions in public job-description text. Dataset: ~11,800 postings sampled (seed 42) from the LinkedIn Job Postings dataset, labelled by LLM-assisted weak supervision and binarised with a MultiLabelBinarizer; stratified 90/10 split. Baseline: TF-IDF with One-vs-Rest Logistic Regression. Transformer: DistilBERT configured for multi-label classification (problem_type = multi_label_classification, sigmoid outputs, binary cross-entropy loss), trained for 3 epochs with batch size 16 and max length 256 on a Colab T4 GPU (ml/Model2_Skill_Extraction.ipynb). The trained artefacts (baseline joblib, label vocabulary JSON, DistilBERT weights) are exported for backend serving.
6.3.4 Model Inference Module
ml_models.py exposes three functions to the rest of the backend: classify_resume(text) returning the predicted category, classify_resume_top(text, k) returning the top-k categories with confidences, and extract_skills(text, threshold, top_k) returning detected skills. The Resume router calls the classifier on both pasted text and uploaded files (with PDF text extraction); the Skill Gap router uses extraction over both the user profile and the target job description, then computes the present/missing partition.
6.3.5 The Interconnected Cascade
The cascade is implemented exactly as designed in Figure 5: completion of a learning item updates the skills table and inserts a skill_learned row into agent_events; background processing consumes unprocessed events, re-evaluates open gap analyses through Model 2, updates learning-plan progress, and sets needs_refresh on affected resumes. Because consumers read from the event table rather than being invoked directly, the cascade is idempotent — reprocessing an event produces the same state — and each module continues to work standalone.
6.3.6 Frontend and Security
The single-page application provides one page per agent (Jobs, SkillGap, Learning, Resume, Interview, CareerPath) plus Dashboard, MockExam, Chatbot, Profile and Login, a persistent sidebar, and an AI-assistant drawer available across pages. State is managed in a lightweight store; authentication uses the Supabase JS client with JWTs attached to backend requests. The interview page implements the browser side of the voice loop: microphone capture, audio upload for transcription, and speech synthesis of questions. All per-user tables enforce row-level security with auth.uid() = user_id policies; API keys for external services are held in server-side environment variables and never exposed to the client.

Limitations
Macro-F1 below target for Model 1 (0.751 vs 0.80): driven by 256-token truncation of long resumes and class imbalance in rare categories. Planned mitigations: 512-token inputs, class weighting or light re-balancing, and additional epochs. The transformer-vs-baseline improvement — the primary scientific claim — is unambiguous.
Model 2 label space restricted to 25 high-frequency skills: tractable and demonstrably useful, but a production system would expand toward the full ESCO vocabulary with hierarchical classification.
Weak labels inherit LLM annotation noise; the manually verified subset mitigates but does not eliminate this.
Job aggregation currently exercises Remotive end-to-end; additional sources are integration-ready but not all continuously synced.
Interview latency depends on external API load; the sub-2-second target is met typically but not guaranteed under provider throttling.
8.0 Conclusion
8.1 Conclusion
This project set out to unify the fragmented career journey into a single intelligent application, and to do so with engineering substance beyond LLM API consumption. Both goals were met. The delivered system implements six cooperating agents over a shared-memory, event-driven architecture that demonstrably cascades insight between modules while preserving standalone operation. Its analytical core is supplied by two models trained specifically for this project: the resume classifier improves on its classical baseline by 16.8 accuracy points (82.3% vs 65.5%), and the skill-extraction model powers reproducible gap analysis independent of external providers. The full stack — React, FastAPI, Supabase with pgvector, and free-tier AI services — operates at effectively zero marginal cost, making equitable access realistic.
Academically, the project exercises the complete breadth of contemporary software engineering — requirements, relational and vector database design, asynchronous API architecture, security, testing — alongside a complete supervised machine-learning workflow from dataset acquisition through deployment behind an inference API.
8.2 Future Recommendations
Model improvements: 512-token inputs, class weighting, expanded skill vocabulary, larger manually annotated evaluation sets.
Deferred agents: Daily Journal & Discussion (skill extraction from journal entries) and monthly Career Progress Summariser.
Automation: application e-mails and follow-ups, weekly digests, WhatsApp reminders, one-click apply with the tailored resume.
Reach: recruiter-side portal over anonymised profiles, multilingual interfaces (Tamil, Sinhala), and a React Native mobile client sharing the same backend.
8.3 Lessons Learned
Baseline first, transformer second: building the TF-IDF baseline before fine-tuning DistilBERT provided both a sanity check and the comparative frame that turned raw metrics into a defensible claim.
Targets should anticipate dataset realities: the original macro-F1 target did not account for severe class imbalance; quantitative targets should be set after exploratory data analysis, not before.
Event-driven decoupling pays off: implementing the cascade through an event table instead of direct agent calls simplified testing enormously and prevented cross-module breakage during iteration.
Free tiers are workable but demand design discipline: caching, background jobs, and per-task model selection were necessary from the start, not optimisations to defer.
Scope control is a continuous activity: adding the mock-exam module was affordable only because two originally planned agents had been consciously deferred early.
